## 好友点击报 RangeError #2006（客户端崩溃，根因已定位并修复）

- 现象：点小镇左侧好友 → `FriendIMWdMediator.update()` → `Container.getChildAt()` 抛
  `RangeError #2006: 提供的索引超出范围`。
- 根因（用 `client_tools/abcdis.py` 反汇编 `webroot/ModuleFriend.swf` 定位）：
  - `FriendIMWd` 是小镇左侧好友 IM 控件，`ITEMS_PER_PAGE = 6`（`FriendIMWd` 的静态常量，
    反汇编取值=6），其 `view.list` 只有 **6 个固定 FriendIMListCell 子对象**。
  - `update()` 对响应里**每一个**好友调用 `view.list.getChildAt(i)`（i 从 0 到
    friends.length-1），并有一段清空间到 `ITEMS_PER_PAGE`。一旦返回的 `friends` 数 > 6，
    `getChildAt(6)` 越界 → #2006。
  - 之前往 `handle_friend_getlist` 注入 14 个人机好友却**未分页**，导致返回 14+ 条 → 必崩。
    原腾讯服是分页的（响应含 page/pageSize/totalCount），私服版漏了分页。
- 修复（`pvz_poc_server.py` 的 `handle_friend_getlist`）：
  - 读取请求 `page`/`pageSize`，按页切片返回：`page_friends = friends[start:start+page_size]`；
    `totalCount = len(friends)`（全量，含人机），`pageSize` 回写。
  - **钳制 `pageSize` 上限为 6**（`FRIEND_WIDGET_MAX=6`）：返回 ≤6 条对 6 格控件永远安全，
    返回更多才崩；原腾讯服行为一致。
  - 同时覆盖 `handle_fuben_getformation_messages`（借卡好友列表，moduleType=5）共用此 handler。
- 验证：导入模块对 `handle_friend_getlist` 做分页单测（stub DTO 构造，避免无关战斗卡加载依赖）：
  - 小镇件请求 pageSize=8 → 钳到 6，返回 6 条，total=15（1 真+14 机）✓
  - fuben pageSize=8 → 6 ✓；请求 3 → 3 ✓；第 2 页(size6) → 3 条 ✓；0 真好友(14 机) → 6 条 total=14 ✓
  - 全部 `friends<=6`，不再越界。
- 关键结论：**凡客户端有固定格子数的列表（如 FriendIMWd 的 6 格），服务端必须分页且单页条数
  ≤ 格子数**，否则 `getChildAt` 越界。私服此前多处"全量返回"是隐患。

  不是 Dto_IdNum）。
- 修复：改为 `物品逐个 pb_bytes(1, pb_varint_field(1,id)+pb_varint_field(2,num))`，不再二次包裹。
- 验证：本地复现两种编码并解码 —— 旧编码 1 个子消息含 id×4（精确复现报错）；
  新编码 4 个独立 Dto_IdNum、各自 id 仅 1 次。`py_compile` 通过。
- 对照：`town_login_rewards.get_stat` 原本就是正确写法（每个物品一个 `_submessage(1, ...)`）；
  `jar_local._item_changes` 里 `pb_bytes(1, build_item_dto(...))` 也是对的（那是
  repeated **Dto_ItemInfo**，用于背包更新），不要误改。

  拼图 45 段、洗炼上限来自 `baptizeLimit.txt`（attack 30万 / def 15万 / hp 90万 / ability 15万）。
- `effective_card_stats(player, cid, level, uid)` 已聚合**全部**系统（拼图/锻造/果实/基因/洗炼/
  觉醒/护甲/时装）——这就是算真实战力的唯一正确入口。
- 实测天花板：q5 六卡 + L300 + 全系统 ≈ **184万**（护甲贡献≈0：`_armor_bonus` 的
  `star_prop` 键是 `fruitType*1000+armorType*100+star*10+substar`，star 合法范围 0..5、
  substar 0..4，超出就取不到 prop）。**300万 达不到**，除非破坏 300 级上限。
- 实现：
  - `pvz_poc_server.bot_develop_card(uin, uid, cid, fraction)`：按同一进度同时推进
    等级(≤300)/拼图/锻造/果实(14槽)/觉醒/护甲/洗炼，全部走 `store.set_card_*` 真实存档。
  - `bots_local`：`_bot_develop_fraction(idx)` ∈ [0,1] 按名次给养成度；`_bot_cards` 只决定
    品质(q1..q5)与等级(≤300)；`ensure_bots` 在卡组重建时调 `develop_card`，然后用
    `card_power_full`（= `card_power(effective_card_stats(...))`）算**真实战力**写进 `bots_state`。
  - 50 个人机（900001-900050）分到 **8 个联盟**（原 3 个 + 新增 阳光联盟/寒霜要塞/熔岩军团/
    量子花园/暗夜花苑），每盟 5-7 人、各有 1 个 leader。
- 验证（真实 import + 临时库）：疯狂戴夫 养成0%/Lv1 → **2,832**；星星果闪耀 24%/Lv74 → 16.6万；
  岩浆坚果 76%/Lv227 → 82万；雷神香蕉 100%/Lv300 → **183万**。等级全程 ≤300。
- 注意：`ensure_bots` 只在 `changed`（卡组重建）时重推养成，避免每次启动写几千行进度；
  卡组的 cid/level 变化会触发 `have != expected` → 清空重建 → 养成重推，链路是自洽的。
